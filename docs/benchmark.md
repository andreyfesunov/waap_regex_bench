# Бенчмарки

## Тестовый стенд

Windows/amd64, Go go1.25.5, Intel Core i5-11400 @ 2.60 GHz, 12 логических процессоров.

## Результаты

### Наивный (baseline) подход

Сначала по паттернам - в исходнике 12172, в конкретном ране было принято 11365, соответственно 807 отклонено.

Почему отклонено? Они используют более богатый синтаксис PCRE, мы оставляем их в rejected, ибо regex в Go не умеет работать с некоторыми выражениями. Их потенциально МОЖНО ПЕРЕПИСАТЬ ИЛИ ДОРАБОТАТЬ, но в рамках задачи решил игнорировать.

Тестовый наивный прогон осуществлялся по 100000 записям (50000 из legitimate, 50000 из malicious).

Теперь по результатам прогона:

| Workers / GOMAXPROCS | Подготовка, с | Матчинг, с | Запись, с | Wall-clock, с | req/s |
|---|---:|---:|---:|---:|---:|
| 1 | 6.678 | 236.156 | 0.038 | 242.874 | 423.45 |
| 4 | 4.499 | 59.275 | 0.060 | 63.836 | 1687.05 |
| 12 | 4.382 | 27.938 | 0.039 | 32.361 | 3579.30 |
| 24 | 4.567 | 27.820 | 0.045 | 32.433 | 3594.48 |

Очевидно, эффективность увеличения воркеров заканчивается на количество логических ядер машины из-за GMP модели.

Так же особенности baseline подхода:

- Сигнатуры регулярок читаем построчно из файла, полностью грузим всё в память, компилируем один раз, затем переиспользуем.
- JSON файлы из датасета грузим последовательно по одной записи, нормализуем, копим в памяти ВСЕ запросы.
- Воркерам выдаём из накопленных запросов батчи по 256 запросов из памяти.
- Для каждого отдельного батча проверяем все принятые regex сигнатуры.
- Результаты всех запросов копим в памяти.
- После поиска записываем результаты по одной JSONL строке.

### Hyperscan

Сначала по паттернам — в исходнике 12172. В режиме common принято 11365:
807 исключены из-за несовместимости с Go regexp, оставшиеся Hyperscan принял
без дополнительных отклонений. Это общий набор ID для сравнения двух движков.

Тестовый прогон осуществлялся по 100000 записям (50000 из legitimate,
50000 из malicious), всего 240300181 нормализованный байт.

Теперь по результатам прогона:

| Workers / GOMAXPROCS | Подготовка, с | Матчинг, с | Запись, с | Wall-clock, с | req/s |
|---|---:|---:|---:|---:|---:|
| 1 | 27.008 | 0.612634 | 0.370 | 27.996 | 163229.58 |
| 4 | 29.810 | 0.143131 | 0.108 | 30.074 | 698660.18 |
| 12 | 26.797 | 0.073423 | 0.118 | 27.024 | 1361963.94 |
| 24 | 26.745 | 0.074631 | 0.109 | 26.992 | 1339931.42 |

В этом прогоне 24 воркера не улучшили время поиска относительно 12. Поиск
занимает короткие интервалы, поэтому однократные замеры чувствительны к шуму.
Компиляция базы заняла 21–25 секунд и входит в подготовку, а не в матчинг:
именно подготовка определяет большую часть полного времени на 100000 запросов.

Для сравнения baseline повторно запускался в том же Docker Linux-окружении
на том же manifest. Ускорение поиска составило примерно 400–480 раз;
полный прогон ускорился существенно меньше. Во всех четырёх конфигурациях
итоговые JSONL совпали полностью.

Особенности Hyperscan подхода:

- Сигнатуры читаем построчно и один раз компилируем в общую базу паттернов.
- JSON файлы читаем по одной записи, нормализуем и копим все выбранные запросы в памяти.
- Воркерам выдаём из накопленных запросов батчи по 256, каждый запрос отдельно сканируем общей базой.
- База общая и неизменяемая. У каждого воркера свой scratch и переиспользуемый буфер ID совпадений.
- Результаты всех запросов копим в памяти, учитывая match / softmatch и порядок probe.
- После поиска записываем результаты по одной JSONL строке и сохраняем manifest принятых паттернов.

#### Полный прогон, режим all

В режиме all Hyperscan принял 11366 паттернов и отклонил 806 — используем
все поддерживаемые им выражения без ограничения совместимостью с Go.

После восстановления log4shell.json прогон охватил весь корпус: 1114166
запросов (1040242 legitimate и 73924 malicious), включая все 220 записей
из восстановленного файла. Объём нормализованных запросов — 5365209223 байта.

Теперь по результатам полного прогона:

| Workers / GOMAXPROCS | Подготовка, с | Матчинг, с | Запись, с | Wall-clock, с | req/s |
|---|---:|---:|---:|---:|---:|
| 12 | 200.173 | 2.074197 | 1.457 | 203.935 | 537155.41 |

Первый полный запуск столкнулся с давлением на память Docker. Повторный
успешно прошёл после точного выделения нормализованных буферов и ограничения
Go GC через GOMEMLIMIT=6GiB, корпус по-прежнему хранится в RAM. Эти изменения
подготовки внесены после замеров на 100000 запросов. На полном корпусе основное
время уходит на подготовку.
