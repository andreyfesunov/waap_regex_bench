# Бенчмарки

## Тестовый стенд

Windows/amd64, Go go1.25.5, Intel Core i5-11400 @ 2.60 GHz, 12 логических процессоров.

## Результаты

### Наивный (baseline) подход

Сначала по паттернам - в исходнике 12172, в конкретном ране было принято 11365, соответственно 807 отклонено.

Почему отклонено? Они используют более богатый синтаксис PCRE, мы оставляем их в rejected, ибо regex в Go не умеет работать с некоторыми выражениями. Их потенциально МОЖНО ПЕРЕПИСАТЬ ИЛИ ДОРАБОТАТЬ, но в рамках задачи решил игнорировать.

Тестовый наивный прогон осуществлялся по 100000 записям (50000 из legitimate, 50000 из malicious).

Теперь по результатам прогона:

| Workers / GOMAXPROCS | Подготовка, с | Матчинг, с | Запись, с | Wall-clock, с | req/s |
|---|---:|---:|---:|---:|---:|
| 1 | 6.678 | 236.156 | 0.038 | 242.874 | 423.45 |
| 4 | 4.499 | 59.275 | 0.060 | 63.836 | 1687.05 |
| 12 | 4.382 | 27.938 | 0.039 | 32.361 | 3579.30 |
| 24 | 4.567 | 27.820 | 0.045 | 32.433 | 3594.48 |

Очевидно, эффективность увеличения воркеров заканчивается на количество логических ядер машины из-за GMP модели.

Так же особенности baseline подхода:

- Сигнатуры регулярок читаем построчно из файла, полностью грузим всё в память, компилируем один раз, затем переиспользуем.
- JSON файлы из датасета грузим последовательно по одной записи, нормализуем, копим в памяти ВСЕ запросы.
- Воркерам выдаём из накопленных запросов батчи по 256 запросов из памяти.
- Для каждого отдельного батча проверяем все принятые regex сигнатуры.
- Результаты всех запросов копим в памяти.
- После поиска записываем результаты по одной JSONL строке.
